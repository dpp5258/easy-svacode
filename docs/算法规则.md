# 睡岗检测 · 算法规则设计文档（角色2 · 算法开发）

> 状态：**草案 v0.1**（实现前定稿）
> 依据素材：44 段手机短视频（趴桌睡为主、坐姿点头瞌睡也有），已用标注工具打好行为真值（阳性=打盹+睡岗）。
> 原则：**不训练模型**；YOLO 只出关键点，睡岗判定全走几何规则 + 时序状态机；最终规则需能复刻到 SVA-server C++ 侧。

---

## 0. 素材与场景约束（规则设计的输入）

| 约束 | 内容 | 对规则的影响 |
|---|---|---|
| 睡姿 | **趴桌睡为主**（头贴桌面、上身趴下），坐姿点头瞌睡其次 | 需要"趴桌级"独立判定路径，不能只靠鼻-肩夹角 |
| 机位 | 近/远**正面、近/远侧面**混合；有时看不见下半身；脸部被遮挡较少但也有 | 特征必须**归一化**（不能依赖绝对像素）；不能假设"一定能看到完整人脸" |
| 场景 | 单人固定工位（将来可能多人） | v1 取画面中置信度最高的 person 框跟踪判定；多人留接口 |
| 误报取向 | **敏感多报优先**（宁可误报写字/低头，不可漏睡岗） | 阈值初始取低（宽松），扫参时沿"提高阈值看误报降多少"方向给曲线 |
| 视频长度 | 5~19s，很多真实睡觉整段 ≤6s | 时序窗口不能太大；持续时长阈值需能在 5s 片段内触发 |

## 1. 调研思路 → 本项目适用性判断

| 调研来源思路 | 本项目是否采用 | 理由 |
|---|---|---|
| 关键点 + 几何特征 + 时序后处理（整体范式） | ✅ 采用 | 既定路线：不训练、便于 C++ 复刻 |
| 固定单帧角度阈值（如俯仰 >30°，CN114360041A） | ⚠️ 不直接采用 | 2D 无相机内参，"角度"受机位影响大；近/远/正/侧混合素材下写死必误报。**只作为对外文档口径，代码用归一化几何量** |
| 基线校准消除视角/个体偏移（SnoozeNet） | ⚠️ 原型期不用，文档展望 | 素材太短无独立校准段；原型用归一化比值近似抗视角；真实部署时再引入"开机录 5s 正常姿态定基线" |
| 滑动窗口占比 / 双阈值（CN114360041A 后半） | ✅ 采用 | 点头打盹是"多次短低头"，纯连续时长会漏；窗口累计占比可兼容 |
| 连续时长触发 | ✅ 采用 | 趴桌/睡岗=长时间低头不动，靠连续时长 |
| 单帧角度 > 阈值即"疑似帧"，统计占比 | ✅ 采用（概念） | 我们的"疑似帧"= hd 超阈值的帧 |
| 关键点置信度过滤 | ✅ 采用 | 低置信度帧不参与累计，防关键点抖动造成误累计 |
| 眼部 EAR / PERCLOS 融合 | ❌ 不采用 | 趴桌/侧面时常看不到眼；全身关键点方案的理由即在此，写进"局限与展望" |
| 人脸被遮挡时用全身关键点兜底（国内期刊思路） | ✅ 采用 | 工位/趴桌场景直接相关 |
| YOLO-Pose 只出关键点 + 行为规则后置（PIFR 跌倒范式） | ✅ 采用 | 技术同源论证 |

> 对外报告口径：**规则为主、模型为辅；模型仅检测，行为判定为几何+时序规则**。

## 2. 模型选择

**选定：`yolo11n-pose`**（COCO 17 关键点，输出张量 1×56×8400）

- 通道布局：`[cx, cy, w, h, conf | (x,y,conf)×17 关键点]`，坐标在模型输入分辨率(640)空间
- 自带 person 检测框 → 单人场景免额外检测器
- 与平台既有 yolo11n 同族 → C++ 集成、报告自洽
- 已确认 ultralytics 官方预导出 ONNX 可直下（11.85MB，无需 torch）

**备选升级路径**（实测后再定）：
- 若趴桌/侧面时头部关键点丢失率高 → `yolo11m-pose` 或 `yolov8s-pose`（更大更准）
- 若仍不足 → 规则层融合平台已有 person 检测(yolo11n 80类) 提供"人在且静止"证据

## 3. 关键点定义（COCO 17 序号，C++ 复刻同款）

```
 0  鼻 nose
 1  左眼  2 右眼
 3  左耳  4 右耳
 5  左肩  6 右肩
 7  左肘  8 右肘
 9  左腕  10 右腕
11  左髋  12 右髋
13  左膝  14 右膝
15  左踝  16 右踝
```

**坐标约定**：图像坐标系 y 向下增大。"头高" = 头部某点 y 值小 → 位置高。

**头部点集合 H**（判断低头用，并集兜底）：`{nose, eyeL, eyeR, earL, earR}` 中**任一点可见即可代表头部**。
**肩中心 S**：`(L_shoulder + R_shoulder)/2`，要求双肩置信度达标（见参数表）。

> 为什么用并集：趴桌时脸朝桌面/侧面，鼻子常不可见但侧脸耳/眼可能可见；只要头部区域任一点可见，就能测"头低没低"。全部不可见 → 本帧标"未知"。

## 4. 单帧姿态特征层（输入一帧 → 输出特征向量）

对画面中置信度最高的 person 框（v1 单人）：

```
gating（任一项不满足 → 本帧 unknown，不参与累计、不清零）:
  G1  person框 conf ≥ c_box
  G2  双肩可见: conf(L5)≥c_kp 且 conf(R6)≥c_kp
  G3  头部点 H 至少 1 点可见(conf≥c_kp)

特征:
  headY = min{ y | p∈H, conf(p)≥c_kp }        # 头部区域最"高"的可见点(并集)
  shY   = (y(L5)+y(R6))/2                      # 肩中心
  boxH  = person框高(必要时夹取: 若框被画面截断,用可见躯干高度近似)

  A. 头肩距离比(主特征, 归一化抗视角/距离):
       hd = (shY - headY) / boxH
       语义: 坐直抬头 → hd 较大(约0.15~0.3, 头在肩上方较远)
              坐着低头 → hd → 0 附近
              趴桌     → hd ≤ 0 甚至为负(头与肩平齐/低于肩中心)
       headDown_now = hd ≤ θ_hd        # θ_hd 初值建议 0.12(敏感), 扫描 0.02~0.25

  B. 趴桌级判定(独立路径, 不强依赖脸部点可见性):
       desk_now = headY 与 shY 平齐或更低(hd ≤ θ_desk, θ_desk 建议 0.0)
                  且(可选强化) 头在画面/框内低位持续
       # 若 H 全不可见 → desk 评估也降级为 unknown; 见 4.1

  C. 头部活跃度(辅助信号, 用于区分"写字微动"与"睡着/点头"调优):
       mv = 滑动窗口 W_mv(如 1.5s)内 headY 的样本标准差(或位移累计)
       用途: 仅作诊断/后续调优; 不阻塞主判定(阳性含点头, 点头也在动)
```

### 4.1 趴桌时"脸不可见"的处理（关键鲁棒性设计）

| 情形 | 处理 |
|---|---|
| H 中 ≥1 点可见 | 正常算 hd / headDown_now |
| H 全不可见，但 person 框 + 双肩可见 | 标 **desk_unknown**：若此前已处于趴桌疑似累计中，继续累计（不清零）；单独维护"deskHoldMs 连续趴桌姿态（由肩线持续低位证据）"计时——v1 先简化为不强制触发、仅防清零 |
| 连续 unknown 超过 `t_unknown_max`(如 3s) | 视为跟踪丢失，重置该 track |

> v1 简化声明：趴桌且脸部完全不可见是最难 case，先保证"能测的都测、不误清零"，实测后据丢失率决定是否升级模型。写进文档勿夸大能力。

## 5. 时序判定层（per-track 状态机）

状态：`NORMAL → SUSPECT(疑似累计) → ALARM → (恢复) → NORMAL`

```
NORMAL:
  每帧若 headDown_now: 进入 SUSPECT, downMs += dt
  每帧若 desk_now:     进入 SUSPECT(或直接走趴桌计时)
  否则维持 NORMAL

SUSPECT(疑似累计, 双阈值并集):
  计时: downMs(低头总时长, 允许点头间隙内的短抬头不打断?见下)
  触发条件(任一满足 → ALARM 并上报 sleep):
    C1 连续低头时长 downMs ≥ T_suspect      # 睡岗/长时间低头, 默认 3000ms(真实秒)
    C2 滑动窗口 W(4000ms)内低头帧占比 ≥ p(0.5) 且窗口内累计低头 ≥ T_suspect
       # 兼容点头打盹: 单次低头<2s, 但反复低头 → 占比达标即触发
    C3 趴桌持续: desk 连续 ≥ T_desk          # 初值 1500ms
  重置回 NORMAL: 连续 GAP(1500ms)无 headDown/desk → downMs=0 回 NORMAL

ALARM(已告警):
  不重复上报; 持续低头保持 ALARM
  连续 GAP 无低头 → 回 NORMAL(允许再次打盹再次触发——素材含多轮工作-打盹)
```

**点头兼容细节**：点头=短低头+短抬头循环。若用"连续低头"会打断。
v1 采用：**downMs 累计时，低头间隙 < gap_tol(500ms) 的抬头不重置**（呼吸式累计）；
v2 若误报上升再改严格连续。

**⚠️ C1 实现要点（已修 bug, 2026-09-03）**：down_run 必须用"低头段起点时间戳"计算
（`down_run = ti - seg_start`，间隙<gap_tol 视为同段），**不可逐帧 `down_run += gap+dt`**——
后者在连续低头时每帧 ≈2×帧间隔，实测 5s 低头会累计成 ~10s（名义 T 减半即触发）。
修复后 T_suspect 为真实秒数；44 段评估数字已按真实口径重跑（§8.5.3）。

**输出**：触发 → `behaviorType="sleep"`（复用既有行为码）+ 触发时刻；供后端告警链路使用。

## 7. 与标注真值/评估的对应

- 标注 JSON：阳性状态 = `打盹犯困(点头)` + `睡岗(睡着不动)`；阴性 = 正常/低头/干扰/离开
- 评估单元：**事件级**——规则在每段视频上跑：
  - 触发时刻落在阳性区间内 → 检出 ✅
  - 触发落在阴性区间 → 误报 ❌
  - 阳性区间全程无触发 → 漏报 ❌
- 输出：参数网格下的 检出率 / 误报率 / 每段触发时刻表，供选点与答辩

## 8. 局限与展望（写报告用，勿夸大）

1. **趴桌且脸部完全不可见**的帧无法测低头角——v1 以"不误清零"兜底，方向是升级模型或融合 person 检测
2. **纯姿态分不开"长时间低头写字"与"睡着低头"**——敏感多报策略下写字可能误报；调优点：头部活跃度 mv + 手腕/笔尖动作为干扰抑制（v2）
3. 无眼部 EAR/PERCLOS——工位视角常看不到眼，这是选全身关键点的理由，也是与 DMS 文献的差异点
4. 固定机位基线校准（录正常姿态定阈值）为真实部署预留的调优手段，原型未用
5. 2D 关键点受光照/遮挡抖动——置信度门控已缓解，剩余抖动靠时序累计平均

## 8.5 真实场景适用性边界（实测：SCB 教室全景 300 张 / 426 个 BowHead 标注）

> 数据来源：SCB-Dataset（Whiffe/SCB-dataset, arXiv 2304.02488）真实大学教室监控全景图，
> 用 yolo11n-pose 检测标注为"低头"(BowHead)的学生，统计"pose 检出且 hd 可算"的比例。
> 报告图：`output/scb_pose_boundary.png`（曲线）、`output/scb_pose_overlay.png`（叠加示例）。

| 人框高(640px空间) | BowHead数 | pose检出+hd可算 | 判定 |
|---|---|---|---|
| <30px | 70 | **0%** | ❌ 不可用 |
| 30-40 | 99 | 4% | ❌ 不可用 |
| 40-50 | 66 | 11% | ❌ 不可用 |
| 50-60 | 39 | 46% | ⚠️ 勉强 |
| 60-80 | 58 | 40% | ⚠️ 勉强 |
| 80-100 | 25 | 56% | ⚠️ 勉强 |
| 100-150 | 49 | **78%** | ✅ 可靠 |
| >150px | 20 | **100%** | ✅ 可靠 |

**结论与工程指引**：
1. **可用边界 ≈ 人框高 100px（640 空间）**，即原图（1080p）人高 ≥ **169px ≈ 画面高 1/6**
2. 教室全景后排学生（通常 30~80px）**pose 睡岗检测基本不可行**；可行区间是前排/近机位/工位特写
3. 已保留 60 张 SCB 样例在 `algo/scb_sample/`（13M），供后续换模型复测
4. **部署建议（三档自适应）**：真实布控前端让用户框选监控目标区域，系统量测区域内人框高：
   - ≥100px(640) → pose+hd 规则（高精度），前端提示"适合"
   - 50~100px → pose 勉强，叠加框级规则（静止+时长）兜底，提示"效果一般"
   - <50px → pose 不可用，自动降级框级规则，提示"建议摄像头靠近目标或放大"

### 8.5.1 ROI 放大实测：等效拉近摄像头（n=212 BowHead 框）

> 实验：同一批 SCB 真值框，baseline=整图 640 推理；ROI=以目标为中心裁剪(PAD=2.5)放大至 640 再推理。
> 报告图：`output/scb_roi_gain.png`。

| 原图人框高 | baseline(全景) | ROI放大 | 提升 |
|---|---|---|---|
| 60-80px | 0% | **73%** | +73% |
| 80-120px | 0% | **78%** | +78% |
| 120-200px | 25% | 73% | +48% |
| >200px | 85% | 78% | -7%(可接受) |
| **总体** | **37%** | **75%** | **+38%** |

**结论**：ROI 放大将远视角 pose 可用率从 37% 提到 75%，把"可用边界"从 ~100px 下探到 ~60px。
**工程前提**：裁剪窗口需留足上下文（PAD≥2.5，本实验 1.2 时大目标被切坏→可用率反而降），
即"放大"必须保留足够人体上下文，不能只贴脸裁。→ 框选放大是真实场景部署的**必要保障手段**，
也是"用户框选区域"交互的真正价值（等效分辨率提升），与 §5 规则本身解耦。

### 8.5.1b 密集邻座诚实复测（n=212：密集163 / 孤立49）

> ⚠️ §8.5.1 的 75% 用"裁剪后取最大置信度 person"，密集邻座场景会误认目标而**虚高**。
> 复测加入"按目标在裁剪图中的期望位置 IoU 匹配回原框"的正确实现（PAD=2.5）。
> 报告图：`output/scb_roi_dense_honest.png`。

| 分组 | baseline | ROI 取最大conf(虚高) | **ROI 位置匹配(诚实)** |
|---|---|---|---|
| 密集(邻座) n=163 | 38% | 80% | **63%** |
| 孤立 n=49 | 45% | 59% | **61%** |
| 全部 n=212 | 40% | 75% | **63%** |

密集子集按框高分档：<80px 0%→**56%**；80-120px 17%→**67%**；120-200px 45%→64%；>200px 50%→62%。

**诚实结论**：
1. 旧实现（maxconf）在密集场景虚高 17pp（80% vs 63%）——**正确实现必须按位置匹配回原目标**，
   不可用"裁剪图里置信度最高的人"当结果（会把邻座低头误当目标）。
2. 即便如此，位置匹配的 ROI 放大仍有效：密集 38%→63%（**+25pp**）、小目标 <120px 从 0~17% 提到 56~67%。
3. 放大增益对小目标最大，密集邻座虽有干扰但放大收益仍大于损失。
4. 真实部署纪律（叠加 §8.5.1 前提）：ROI 裁剪 → 推理 → **IoU 位置匹配回原框** → 坐标映射回原图，
   不得用 maxconf；截图/推送坐标仍在原图空间。

### 8.5.2 机位状态 → 证据档位（云台/移动摄像头）

| 机位状态 | 可用证据 | 行为 |
|---|---|---|
| 固定机位(或微抖) | ROI + pose(hd) + 时长静止 | 正常检测 |
| 云台转动中 | pose 单帧仍可算，但时序"静止/持续"不可信；ROI 区域出画 | **暂停判定/只缓存不触发**（画面剧变保护：连续多帧无人/目标跳变 → 重置状态） |
| 转动停止→预置位 | 回到固定档 | 重新累计 |

> 睡岗语义="长时间不动"，要求机位相对目标静止；云台巡航检测不属本方案范围（需 SLAM/运动补偿）。
> 场景切换保护可用 44 段中 33/34/35（人员离开/进入）验证：应重置不误报。

### 8.5.5 近景多人 + CPU 预算设计（验收口径：近景 2~5 人共存场景）

> 背景：验收/演示为**近景多人**（画面内 2~5 人，非教室全景远视角）。已澄清：
> 多人 ≠ 吃 CPU——yolo11n-pose **一次推理输出整帧全部 8400 候选**，画面 1 人或 5 人推理耗时相同
> （实测 CPU 34ms/帧），多人的真实增量仅是 NMS + 每人几何/状态机（微秒~毫秒级，可忽略）。
> CPU 压力真正来自**推理频率**，与人数无关 → 靠节流控制，不由"单人/多人"决定。

**一、CPU 预算（推理帧率 vs 人数）**

```
每帧推理固定成本(640×640 CPU): ~34ms → 单核最多 ~29fps
多人附加成本: NMS+每人hd+状态机 ≈ <1ms (忽略)

平台自带节流保护(Worker.cpp:625-639): 
  每路布控 checkFps → 距上次推理 <1000/checkFps ms 的帧跳过推理
  且每6s自适应回写 checkFps: CPU 忙→自动降(实测 1.6~5fps 区间)

CPU 预算结论:
  · 单路布控近景多人, 建议 checkFps 上限 5~10 (默认即可, 平台自适应)
  · 多人不额外加推理成本; 若要同时跑多路布控/多算法, 总推理率需摊分
  · 若要更高帧率 → 缩小推理输入(模型640固定)不可行, 只能换机/GPU/降路数
```

**二、多人检测与判定架构（v2 设计）**

```
检测层(每帧):
  整帧 640 推理 → 解码全部 person 框+17关键点
  → NMS 去重(IoU 0.5) → 按 conf 排序 → 保留前 K 人 (K 默认 5, 可配 1~10)
    [CPU紧张 → 降 K 或降 checkFps; 场景空旷 → 提 K]
  → 每人算单帧特征(复用 §4: gating + hd; 带 box 供追踪)

追踪层(跨帧):
  IoU 贪心匹配: 当前帧框 与 已有 tracks 求 IoU, >0.3 归并同 trackId, 否则开新 track
    (平台 C++ Worker.cpp:662-667 已实现同款, 原型照抄; 规则状态机不变)
  track 生命周期: 连续丢失 >t_lost(如2s) 删除

判定层(每 track 一条, 复用 §5 完整状态机):
  每个 track 独立跑 C1/C2/C3(θ_hd/T_suspect 等参数共用)
  → 各自触发记录 {trackId, t, chan, box}

告警层(防刷屏策略):
  一次布控事件窗口内(如 eventWindow=10s)只报首个触发的 track → 抑制同事件重复
  恢复(GAP后)可再报新事件
  上报携带: trackId + 人框坐标(原图) + 触发通道
```

**三、参数表（多人新增/复用）**

| 参数 | 初值 | 说明 |
|---|---|---|
| `K` 每帧最多判定人数 | **0 = 全量** | 对齐平台 per-detect 全量(§8.5.6); 可设 K>0 作 CPU 预算(conf 前K) |
| `NMS_IoU` | 0.5 | person 框去重(多人同框) |
| `match_IoU` | 0.3 | 跨帧 track 匹配(平台同款) |
| `t_lost` track 删除 | **30帧 或 4s** | 对齐平台 TemporalContext(missed>30 或 lostMs>4000ms) |
| `eventWindow` 防刷屏 | **原型未实现** | Python 原型靠状态机 GAP 防重复; C++ 接入由平台事件机制(restartCooldown 等)承接 |
| `checkFps` 推理节流 | 平台自适应 | 建议上限 5~10(C++ 侧; Python 原型无此概念) |
| `still_speed` 静止阈值 | **40px/s** | 手机近拍素材实测值; 固定监控用平台默认 6~12 |
| 共用 §6 全部姿态/时序参数 | θ_hd=0.12 等 | 多人共用一套阈值 |
