> 说明：文中所有 `文件:行号` 均指向当前仓库已确证的位置；标注「建议」的内容为待实现决策，其余为现状事实。

## 0. 结论速览

1. 本系统已内建 **ONNX Runtime + 2 个 80 类 COCO 检测模型**（yolo11n / yolo26s），推理管线是现成底座——任务2 不需要引入推理库，只需**在既有框架内新增一个 YOLO-Pose 模型引擎**。
2. C++ 侧**已有一个框级启发式 `sleep` 行为规则**（静止 + 宽高比异常≈躺卧），但它不是 YOLO-Pose，且**链路最后一跳被掐断**：
   - Java 入站白名单不含 `sleep` → 事件被静默丢弃（不告警入库、不推送、前端不可见，且无报错）。
   - DB 缺 `BEHAVIOR_SLEEP` 模板；前端告警记录页缺 `sleep` 中文映射。
3. **总体策略：复用 `sleep` 行为码；先修通链路并验证，再接 YOLO-Pose 判定源。** 新 pose 判定与旧框级判定是同一规则的两个实现，下游补丁一次打对。
4. 现状推理为**串行**（全局锁），「与原有 YOLO 并行」在代码层面是待实现的线程化改造，需如实表述。

## 3. 总体策略

### 3.1 关键决策：YOLO-Pose 版**复用 `sleep` 行为码**

- 新 pose 睡岗判定最终输出仍是 `behaviorType="sleep"`，因此第 4 节 Phase 0 的通路补丁**原样适用**，一次打对。
- 避免新造 `sleep_pose` 码 → 否则 Java 白名单、常量映射、前端 label、DB 模板每处都要再维护一套，且与旧 `sleep` 语义打架。
- 报告口径：**用 YOLO-Pose 关键点增强原有 `sleep` 规则**（同一规则、更强判定源）。

### 3.2 实施顺序：先通后优，薄垂直切片

```
Phase 0  修通链路（几行 Java + 一条 DB 模板 + 一处前端映射）
Phase 1  冒烟验证（伪造 sleep 事件 → 后端落库/推送；不依赖新模型）
Phase 2  YOLO-Pose 模型导出 + C++ 引擎接入
Phase 3  姿态睡岗判定（关键点 → 姿态规则）
Phase 4  （可选）并行调度改造
Phase 5  模型产物与部署交付
Phase 6  端到端回归
```

理由：先有「绿色基线」，之后 pose 引擎出错可立即定位到新代码；且可**分阶段演示**、分阶段验收。

### Phase 3 — 姿态睡岗判定（这是核心逻辑，最值得写报告）

- 语义：YOLO-Pose 只给骨骼点，**不直接输出「睡着」**。需自行定义可计算姿态规则，例如：低头角度 = 鼻-颈连线的俯仰角低于阈值；趴桌 = 头关键点持续低位 + 静止；并结合**多帧/时长**过滤。
- 复用现有时序基础：事件级 `ruleMinHits`/`ruleHitWindowMs`（`Scheduler.cpp:1586`）做 N 帧确认；也可在 `Worker.cpp` 行为段自建 per-track 状态机（现有 `updateTemporalTracks` :738 是给 box 的）。
- 建议把「单帧姿态特征」与「跨帧睡岗判定」拆成两层：前者可单测，后者可复用链路。

### Phase 4 —（可选）「与原有 YOLO 并行」

## 5. 关键设计决策汇总

| 决策 | 选项 | 选择 | 理由 |
|---|---|---|---|
| 新睡岗输出行为码 | `sleep` / `sleep_pose` | **复用 `sleep`** | 通路补丁一次打对；与既有规则同语义 |
| 与旧 YOLO 并行 | 真线程并行 / 同布控多算法任务 | **先多算法任务（串行）** | 风险低、功能正确；并行如实标注为待办 |
| 判定实现层次 | 全部塞行为引擎 / 拆姿态层+时序层 | **拆两层** | 姿态可单测；时序复用现成 N 帧确认 |
| 模型族 | yolov8n-pose / yolo11n-pose | **yolo11n-pose** | 与既有 yolo11n 同族，报告自洽 |

## 6. 难点与风险

**难点排序（由高到低）**
1. 睡岗**语义定义**：姿态 ≠ 睡着；需把「睡岗」翻译成可计算的姿态规则（低头角/趴桌/久静）。
2. 单帧姿态噪声大 → **多帧滤波/防误报**是价值所在，也是「改造原有紫色模块」的重点。
3. 关键点数据接入现有行为引擎：`DetectObject` 无关键点字段，需扩展结构或并行通道。
4. 多端注册一致性：`initAlgorithm` / `resolveAlgorithm` / `av_algorithm` 三处同步，少一处即「不支持的算法」（仓库 `on_yolo26s_miner` 即此类未接线活教材，`data_20250520.sql:73`）。
5. Pose 输出布局与现有解码器不同，需新写后处理。
6. 部署与演示素材：模型文件是运行时产物、需造「真人长时间睡岗」的验证视频。

**主要风险**
- Java 白名单静默丢弃（Phase 0 未做则全线不通且不报错）。
- 「并行」承诺与代码现状不符 → 答辩被问倒。
- 真机端到端依赖整套部署 + 模型 + RTSP/视频源，成本高；用 Phase 1 的伪造事件 + 姿态层单测作为替代验证。
